# KnowledgeVault / MyKV Managed Pilot — Transaction Boundary

## Intake boundary
Identify the owner, target storage/file surface, desired file-based continuity scope, sensitivity constraints, backup expectations and any optional provider/runtime capability requested. Baseline file-only deployment requires no hosted service, SDK or AI provider.

## Deliverables
A scoped pilot may provide a clean KnowledgeVault package/deployment, installation receipt, owner-controlled folder/continuity structure, instance identity/projection, operating guidance, integrity verification and a bounded continuity/reconstruction exercise.

## Exclusions
No credential custody in ordinary KV files, no automatic provider authentication/synchronization, no undeclared data movement, no automatic AI corpus exposure, no relationship-tier mutation, and no production InTr/SKAP activation unless separately admitted and evidenced.

## Acceptance
Complete when the agreed file-based vault is delivered/initialized, applicable package or installation integrity checks pass, owner-specific private content is not silently overwritten, and the customer can inspect the agreed continuity structure and receipts.

## Commercial terms
Pilot price, migration scope, storage/provider work, support, retention and any optional governed integrations are separately quoted. No universal price is asserted.

## Evidence / receipt
Use release/package verification where applicable plus installation receipt, instance identity, agreed migration/continuity evidence and customer delivery/acceptance evidence.

## Unreleased substrate not sold
The pilot may use the released v0.1.9 baseline and separately identified current source capabilities, but post-v0.1.9 MyKV/Interlock/provider work on main is not represented as contained in that immutable release. Production InTr/SKAP/provider activation is not sold as already released or proven.
